# Storage schema — Antigravity Memory Skill

This document defines the on-disk storage schema: entry format, the five-layer
layout, the generated router, the search index, store resolution, deduplication,
and the forgetting policy. It implements coordinator spec §4 (store layout and
entry format), §6 (lessons and thinking journals), and §10 (token budget and
forgetting policy). The spec is the single source of truth; where this document
and the spec disagree, the spec wins and the disagreement is listed in
§10 (Open points) for the coordinator to reconcile.

Scope note: this document covers storage shape only. Retrieval scoring is
spec §5 (implemented in `scripts/memory.js` and justified in
`docs/math-model.md`); the CLI surface is spec §8; secret blocking is spec §7.
No Antigravity product format is defined here — every Antigravity path or
integration format this skill relies on comes from spec §9, and nothing else
about Antigravity internals is assumed.

## 1. Store layout (five layers)

A store is a directory with this fixed layout:

```
<store>/
  00_MEMORY_ROUTER.md            # GENERATED by `memory.js index`. Never hand-edit.
  01_user-profile/*.md           # user facts, preferences
  02_episodic/*.md               # session summaries, decisions, work logs
  03_semantic/*.md               # durable knowledge, project facts, conventions
  04_procedural-lessons/*.md     # lessons from mistakes (see §4)
  05_thinking-journal/*.md       # thinking journals (see §5)
  index.json                     # search index, rebuilt automatically when stale (see §7)
```

What belongs where:

| Directory | Holds | Example |
| --- | --- | --- |
| `01_user-profile/` | Facts about the user and their standing preferences | Preferred summary style, "run tests before done" |
| `02_episodic/` | What happened in a session: summaries, decisions made, work logs, open follow-ups | A refactor session summary |
| `03_semantic/` | Durable, project-scoped knowledge: facts and conventions that stay true across sessions | "example-api: Node >= 18, zero dependencies" |
| `04_procedural-lessons/` | Lessons from mistakes, with machine-checkable triggers | "Stale mock leaked between test cases" |
| `05_thinking-journal/` | Reasoning records for multi-step tasks, written before acting and closed after finishing | A refactor journal |

Only the journal filename is fixed by the spec (see §5). Filenames in the
other layers are the CLI's choice, but they must be stable and unique within
the store, because `index.json` points at entries by file path (see §7).

## 2. Store resolution order

The store root is resolved in this order (spec §4):

1. The `--dir` flag, if given.
2. The `AGMEM_DIR` environment variable, if set.
3. `<cwd>/.agents/memory`, IF a `.agents/` directory exists in the current
   working directory.
4. `$HOME/.antigravity-memory` (fallback).

For a project install, the user or agent sets `AGMEM_DIR` to the project's
`.agents/memory`, or the hook scripts pass `--dir`. These are the only store
paths this skill uses; the skill never writes into a real Antigravity config
directory on its own.

## 3. Entry format

One Markdown file per entry. Every entry file has YAML frontmatter delimited
by `---` lines, followed by a body:

```markdown
---
id: m_<10 hex chars>
category: user | preference | project | decision | lesson | fact | episodic | other
tags: [tag1, tag2]
source: user | tool-output | file-path | url | session
confidence: verified | user_stated | inferred
importance: 1..5   # 5 = user-asserted or load-bearing; 1 = trivial
created_at: <ISO 8601>
updated_at: <ISO 8601>
access_count: 0
error_signature: ""   # lessons only: comma-separated trigger substrings, lowercase
trigger: ""           # lessons only: short situation description
prevention_check: ""  # lessons only: command or checklist item to run first next time
---

<body: one self-contained fact, or the lesson/journal content>
```

### Field reference

| Field | Required | Type / values | Rules |
| --- | --- | --- | --- |
| `id` | Yes | String, `m_` + exactly 10 lowercase hex chars | Generated from `crypto.randomBytes(5)`. Unique per entry. Never reused after delete. |
| `category` | Yes | Closed enum: `user`, `preference`, `project`, `decision`, `lesson`, `fact`, `episodic`, `other` | Pick the closest value; do not invent new categories. Journals use `other` (see §5). |
| `tags` | Yes | YAML list of short lowercase strings | Free-form, but keep them short and reusable across entries so search can group by tag. Empty list `[]` is allowed. |
| `source` | Yes | Closed enum: `user`, `tool-output`, `file-path`, `url`, `session` | Where the entry came from. `user` = the user stated it; `tool-output` = a tool/test/lint result; `file-path` = read from a repo file; `url` = read from a web page; `session` = recorded during a session. |
| `confidence` | Yes | Closed enum: `verified`, `user_stated`, `inferred` | `verified` = checked against a real run, file, or tool output. `user_stated` = the user said it. `inferred` = the agent's own reasoning or guess — never present as verified. |
| `importance` | Yes | Integer 1–5 | 5 = user-asserted or load-bearing (other entries or the router depend on it). 1 = trivial. Importance drives router truncation (§6) and the forgetting policy (§9). |
| `created_at` | Yes | ISO 8601 timestamp | Set once at creation, never changed. |
| `updated_at` | Yes | ISO 8601 timestamp | Updated on every content, tag, or source change, including dedupe merges (§8). |
| `access_count` | Yes | Non-negative integer | Starts at `0`. Incremented when the entry is read through the CLI. |
| `error_signature` | Lessons only | Lowercase, comma-separated trigger substrings | Used by `lesson-check`: a lesson matches when one of its substrings (case-insensitive) appears in the given text. Keep substrings short and distinctive (e.g. `test failed`, `assertionerror`), not whole sentences. Omit this field from non-lesson entries. |
| `trigger` | Lessons only | Short situation description | The situation pattern that should recall this lesson. Mirrors the body's `Trigger:` section. Omit from non-lesson entries. |
| `prevention_check` | Lessons only | Exact check or command to run first next time | Must be actionable, e.g. a command to run or a checklist item — not vague advice. Mirrors the body's `Prevention:` section. Omit from non-lesson entries. |

### Body rules

- The body is one self-contained fact for ordinary entries: it must make sense
  without reading any other file.
- Body max 2000 characters for ordinary entries. Split longer facts into
  multiple entries instead of writing one long file.
- Lesson and journal bodies follow the mandatory section structures in §4
  and §5 below; they are structured records rather than single facts, so they
  are kept focused instead of padded, and the shipped templates stay under
  the 2000-character cap as well.
- Never store secrets in a body or in frontmatter. Secret blocking (spec §7)
  rejects card/national-ID digit runs, Google API keys, token formats, PEM
  private-key headers, and password assignments on every save, lesson-add,
  and journal-note.

### Example entry (shortened; full examples ship as templates — see §11)

```markdown
---
id: m_a1b2c3d4e5
category: user
tags: [communication, workflow]
source: user
confidence: user_stated
importance: 4
created_at: 2026-10-26T09:00:00Z
updated_at: 2026-10-26T09:00:00Z
access_count: 0
---

The user prefers short status summaries: what changed, which checks ran, and
what is still open.
```

## 4. Lessons (`04_procedural-lessons/`)

A lesson is an entry with `category: lesson` plus the three lesson-only
frontmatter fields (`error_signature`, `trigger`, `prevention_check`). Its body
MUST contain all seven sections, in this order:

```
Title: <short name>
What: <symptom / what went wrong>
Why: <root cause, evidence-backed, one sentence>
Where: <file / command / tool>
Lesson: <what to do differently>
Trigger: <situation pattern that should recall this lesson>
Prevention: <exact check/command to run before similar work>
```

- `Why` must be evidence-backed (a failing output, a file, a test result),
  not a guess. One sentence.
- `Trigger` in the body and the frontmatter `trigger` field carry the same
  situation description; `Prevention` in the body and the frontmatter
  `prevention_check` field carry the same check.
- Capture triggers — the agent MUST record a lesson when: a test, lint, or
  build fails; a tool errors; output is wrong; or the user corrects the
  agent. The lesson is written BEFORE retrying where possible, and always
  before reporting done after a failure.
- `lesson-check <text>` matches lessons whose `error_signature` substrings
  (case-insensitive) appear in the text, ranked by number of matched
  substrings, then importance.

## 5. Thinking journals (`05_thinking-journal/`)

A journal is the substitute for a hidden chain-of-thought: the agent's
reasoning written to a file so it can be re-read and audited later. It never
claims to be the model's internal reasoning — it is the record the agent
wrote deliberately.

- Filename: `<YYYY-MM-DD>-<slug>.md` (e.g. `2026-10-26-refactor-validation.md`).
  The shipped template is the exception: it is named `_example-journal.md`
  so the indexer skips it (see §11).
- Frontmatter: the standard entry frontmatter from §3. Spec §4's category
  enum has no `journal` value, so journals use `category: other` rather than
  inventing a value outside the closed enum. `source` is normally `session`;
  `confidence` is normally `inferred`, because a journal records reasoning
  (its outcome section may still report verified check results).
- The body MUST contain all nine sections, in this order:

```
## Goal
## Acceptance criteria
## Hypotheses
## Options considered (and rejected, with reason)
## Assumptions
## Verification plan
## Progress notes
## Outcome
## Lesson link
```

- `Options considered (and rejected, with reason)` must name at least the
  options that were actually weighed, each with its rejection reason. An
  option listed without a reason does not satisfy the section.
- `Lesson link` points at the lesson file created from this task (a store-
  relative path such as `04_procedural-lessons/<file>.md`), or states
  explicitly that no lesson arose (e.g. "None — task completed with no
  failure or correction").
- Protocol: for a task of more than ~3 steps, `journal-start` (goal, criteria,
  options) runs BEFORE acting, `journal-note` appends after each major step,
  and `journal-close` (outcome + lesson link) runs at the end. A journal
  without `Outcome` and `Lesson link` is still open.

## 6. Router (`00_MEMORY_ROUTER.md`)

- GENERATED by `node scripts/memory.js index`. Never hand-edit the generated
  file: regeneration overwrites it completely.
- Hard cap: max 40 lines. `index` enforces the cap by truncation and FAILS
  if the file would still exceed 40 lines after truncation logic — truncation
  is not optional.
- Sections, in this exact order:

```
# Memory Router
## User
## Active projects
## Key decisions
## Lessons — triggers
## Open threads
```

- Content rules: top user/preference facts under `## User`; active projects
  under `## Active projects`; key decisions under `## Key decisions`;
  lessons under `## Lessons — triggers`; open threads under
  `## Open threads`. Every item is exactly one line pointing at its entry
  file (store-relative path). Lesson lines use the form
  `trigger → file`, e.g.:

```
- tests fail right after a refactor → 04_procedural-lessons/_example-lesson.md
```

- Truncation: when the router would exceed 40 lines, drop items by
  importance first (lowest importance goes first), then by recency (oldest
  goes first). The 40-line count includes headings and the title line.
- Progressive disclosure: the router is a pointer file, not a summary store.
  The agent reads the full entry file on demand when a router line is
  relevant; the router itself stays small so it fits the token budget
  (spec §10).

### Router excerpt (format sample; the shipped template is §11)

```markdown
# Memory Router
## User
- Prefers short status summaries and tests before "done" → 01_user-profile/_example-user.md
## Active projects
- example-api: Node >= 18, zero dependencies, test and lint before done → 03_semantic/_example-fact.md
## Key decisions
- Keep the refactor zero-dependency; move tested code as-is → 05_thinking-journal/_example-journal.md
## Lessons — triggers
- tests fail right after a refactor → 04_procedural-lessons/_example-lesson.md
## Open threads
- Re-run the full suite after review comments, before merging → 02_episodic/_example-session.md
```

## 7. Search index (`index.json`)

- `index.json` lives at the store root and holds one record per entry:

```json
{
  "id": "m_a1b2c3d4e5",
  "file": "01_user-profile/_example-user.md",
  "category": "user",
  "tags": ["communication", "workflow"],
  "tokens": ["user", "prefers", "short", "status"],
  "importance": 4,
  "updated_at": "2026-10-26T09:00:00Z",
  "access_count": 0,
  "error_signature": "",
  "last_accessed_at": null
}
```

- Field notes:
  - `file` is the store-relative path to the entry file.
  - `tokens` are the entry's search tokens, produced by the spec §5
    tokenization (lowercase, split on non-alphanumeric, drop tokens shorter
    than 2 characters, drop a small EN + VI stopword list).
  - `error_signature` is the lesson's frontmatter value, or `""` for
    non-lesson entries (non-lesson entries carry no signature).
  - `last_accessed_at` is an ISO 8601 timestamp (or `null` if the entry has
    never been surfaced). It is refreshed by `search`, `context`, and `get`
    in `index.json` ONLY — entry files are never rewritten on reads, to
    avoid write churn. Index rebuilds preserve previous values (see §9).
  - Top-level container (coordinator decision, 2026-10-26):
    `{ "version": 1, "generated_at": "<ISO>", "entries": [ ...records... ] }`.
    Consumers must still read records through the CLI, not by assuming the
    wrapper shape will never change.
- Rebuild-when-stale rule: if any entry file is newer than `index.json`,
  rebuild the index from the entry files and rewrite `index.json`. The
  `index` command also regenerates the router in the same run.
- Search must work even with no index (fall back to scanning entry files).
- Corrupt entry files are skipped with a warning on stderr; a corrupt file
  never crashes a whole command.
- Writes are atomic: write a temp file, then rename into place. This applies
  to entry files and to `index.json`.

## 8. Deduplication

- A save whose body is a duplicate of an existing entry — same normalized
  body — MUST NOT create a second file.
- Instead, the existing entry is updated: merge in any new tags, update
  `source` if the new save carries a stronger or different source, and bump
  `updated_at`. The `id` and `created_at` of the existing entry do not
  change.
- "Normalized body" (coordinator decision, 2026-10-26): lowercase the body,
  collapse every run of whitespace to a single space, and trim. Implemented
  identically on save and on lookup in `scripts/memory.js`. Template
  authors must not rely on a particular normalization: two entries that
  differ in wording are different entries, even if they mean the same thing.

## 9. Forgetting policy

Forgetting is a user-reviewed listing. It is NEVER automatic deletion.

- `index --stale` lists stale candidates for user review. It does not delete
  anything.
- Stale candidate: an entry with `importance <= 2` AND last access older
  than 180 days, where last access = the index record's `last_accessed_at`,
  falling back to the entry's `created_at` for entries never surfaced.
  (Coordinator decision, 2026-10-26: `updated_at` is deliberately NOT used
  as an access proxy — an old but frequently read entry must not be
  flagged merely because its content has not changed.)
- Protected entries: NEVER flag or delete an entry with
  `confidence: user_stated` AND `importance >= 4` without explicit user
  confirmation. (The shipped user-profile template — `user_stated`,
  importance 4 — is an example of a protected entry.)
- Anything the user confirms for removal is deleted through the CLI's
  `delete` command, not by hand-editing the store, so the index and router
  stay consistent.

## 10. Coordinator decisions (2026-10-26, assembly)

These were open points in the spec; each is now settled and implemented in
`scripts/memory.js` as shipped:

1. **Underscore-skip rule — RESOLVED, implemented.** Files whose basename
   starts with `_` or `.` are never indexed (verified in the entry scanner).
   Shipped templates (`_example-*.md`) are therefore safe.
2. **Journal category — RESOLVED, moot.** Journals in `05_thinking-journal/`
   are never scanned as entries at all, so their frontmatter `category`
   value is informational only. The entry scanner's closed category enum is
   unchanged, and no undocumented category is accepted for real entries.
3. **Dedupe normalization — RESOLVED.** Lowercase + collapse whitespace +
   trim, applied identically on save and lookup (see §8).
4. **Stale measurement — RESOLVED.** `last_accessed_at` in the index record,
   refreshed by `search`/`context`/`get`, falling back to `created_at`
   (see §7, §9). `updated_at` is not used as an access proxy.
5. **Index container shape — RESOLVED.**
   `{ "version": 1, "generated_at": "...", "entries": [...] }` (see §7).
6. **Filenames — RESOLVED.** Entry files are named `<id>.md` (the CLI
   enforces filename = entry id); journals are `<YYYY-MM-DD>-<slug>.md`.

## 11. Shipped templates

These files ship with the skill under `memory-templates/` as format samples.
They are NOT store entries: they are never copied into a store, and (per the
underscore convention in §10.1) they are never indexed. Real entries are
created only through the CLI (`save`, `lesson-add`, `journal-start`).

| Template | Models |
| --- | --- |
| `memory-templates/00_MEMORY_ROUTER.md` | Router format: 5 sections in order, one line per entry, 16 lines total (within the 40-line cap). Header states it is a SAMPLE: the real router is generated by `index` and must not be hand-edited. |
| `memory-templates/01_user-profile/_example-user.md` | User entry: `category: user`, `source: user`, `confidence: user_stated`, importance 4 (protected under §9). |
| `memory-templates/02_episodic/_example-session.md` | Episodic entry: session summary holding a decision and an open follow-up (the lines the router's Key decisions and Open threads sections point at). |
| `memory-templates/03_semantic/_example-fact.md` | Project entry: durable project convention for an example project. |
| `memory-templates/04_procedural-lessons/_example-lesson.md` | Lesson entry: all three lesson-only frontmatter fields plus all seven mandatory body sections. |
| `memory-templates/05_thinking-journal/_example-journal.md` | Journal entry: standard frontmatter plus all nine mandatory body sections. |

All template content is generic coding-agent material (a refactor, a test
failure, test/lint commands). No template claims any Antigravity API, file
format, or behavior beyond what spec §9 states, and no template contains a
secret or a real credential.

## 12. Token budget — measured costs and snippet rules (v1.0.1)

Budget principle (user requirement 2026-10-26): do not overspend tokens,
but never save tokens by hiding the information that prevents a mistake.
Costs below are measured from the code, using ~4 characters per token; a
full entry body is capped at 2000 characters (§3), so one `get` costs at
most ~0.6k tokens.

| Call | Default size | Approx. cost | What it shows |
| --- | --- | --- | --- |
| `context` | Router (max 40 lines) + top 30 entries | Router ~1.2k + entries ~2.9k ≈ 4.1k tokens | Session-start load; entries sorted by category priority (user, preference, project, decision, lesson, fact, episodic, other) |
| `search` | Top 8 hits | ~0.8k tokens | Score, coverage, category, importance, file + one snippet line per hit |
| `get <id>` | One full entry | ≤ 0.6k tokens | Full frontmatter + full body |
| `lesson-check <text>` | Matching lessons | Small (one line per match + prevention) | Title + prevention per matching lesson |

Snippet rules (the correctness side of the budget):

- Non-lesson hits in `search`/`context` show the first non-empty body line,
  capped at 300 characters. That is a preview, not the entry.
- Lesson hits show `Lesson: ... | Prevention: ...` (extracted from the
  lesson body's mandatory sections), capped at 400 characters. Rationale:
  a lesson body is a 7-line Title/What/Why/Where/Lesson/Trigger/Prevention
  layout, so a first-line snippet would show only the title and hide
  exactly the parts that stop a repeated mistake. Before v1.0.1, search
  and context snippets had this flaw.
- The router (max 40 lines) is a pointer file: lesson lines carry the
  trigger, not the lesson text. The agent reads the full entry (`get`)
  whenever a line, snippet, or trigger does not settle the question —
  see SKILL.md ("Read the full entry file...").
- Nothing here cuts the `context` default of 30 entries: in a large store
  the category-priority sort keeps user/preference/project/decision first,
  and lessons remain retrievable on demand via `lesson-check`/`search`/`get`.
  Cutting the default to save ~1k tokens per session would risk dropping
  exactly the entries the agent needs, which is the failure mode this
  section exists to prevent.
